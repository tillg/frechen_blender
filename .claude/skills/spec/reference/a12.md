# A12 in this project

What the spec skills need to know about A12 and about agents12 specifically. Read it when a
change touches models, the client or the server — i.e. almost always.

## Where things live

| Thing | Path | Notes |
|---|---|---|
| A12 models (modelling-time) | `import/models/` | Converted to runtime models in `build/wcf-output/data/models` by the root task `gradle convertModels`; the server loads that folder at start, never `import/models/`. The frame Application Model is `import/models/ControlPlane_Ap.json` (`appModelName` in `setup.json`); platform models in `import/models/platform/{config,runtime,relationships,screens}`. User Management's models come from its jar (`classpath:um/basic/models`, imported before the project's). |
| Application models and seed | `${AGENTS12_APPLICATION}` (`.env`, default `applications/family-office/`): `models/`, `seed/`, `demo/` | `gradle convertApplicationModels` → `build/application/data/models`, imported after the platform's; seed and demo data loaded by `init-data` into an empty database (`just flush-seed`). Without an application nothing starts. |
| Authorization | `import/auth/roles.yaml`, `import/auth/childAuthorizationDefinition.json` | Roles and ABAC definitions imported at start. |
| Client app | `client/src/` — `app/` (setup, layout), `modules/` (custom modules, `modules.generated.ts` from `npm run generate`; `userManagement.tsx` registers the embedded User Management for `userManagementAdmin`), `sagas/`, `components/`, `localization/` | A12 engines composed in `client/src/appsetup.ts`: Overview + `withRelationshipFormEngine` + CRUD + Tree + Content — the template's **legacy** Relationship Engine architecture (bindings), matching `relationshipEngineMode: "legacy"` in `import/settings.json`. |
| Server app | `server/app/src/main/java/com/mgmtp/a12/template/server/` | Spring Boot + A12 Data Services + embedded A12 User Management (basic mode, `um/`); attachment handling; `devstack/` reads the stack number. |
| Server init | `server/init/` | Model/document import and migrations; with `init-data` it loads the seed `import/data/` (`seed/SeedGate` only into an empty database). |
| Dev infra | `just up` / `just down` (`scripts/stack.sh`); ports `84` + stack number + role digit (Keycloak `84n9`, compose Postgres `84n3`), see `specs/system/dev-stacks.md` | |
| A12 release line | `gradle.properties` → `a12ReleaseLine=2026.06` | Pin doc searches to this release. |

Model file naming follows the template: `<Name>_Dc.json` (Document Model), `_Fm` (Form Model),
`_Ov` (Overview Model), `_Ap` (Application Model); Relationship, CDM, Query and Tree Models follow
the same `<Name>_<Suffix>.json` scheme. Check `specs/system/models.md` for the current inventory.

## A12 helpers — use when available, state the fallback when not

These are plugins installed per user, not shipped with the repo. Each skill checks with the Skill
tool; a missing skill is reported in one line and the fallback used.

| Need | Skill / tool | Fallback |
|---|---|---|
| Decide the A12 approach for a feature (models vs code, client vs server, engines, authorization) | `a12-solution-architect:research-a12-solution` | A12 docs MCP (`search_a12_docs`, release 2026.06) + the project's `specs/system/architecture.md` |
| Create or change models | `a12-modeling-support-2026-06:model-a12-entities` (single or multi model) | edit the JSON by hand following an existing model file and the docs |
| Validate models | `a12-utilities:validate-a12-models` | `gradle :import:build` |
| Repair validation errors | `a12-modeling-support-2026-06:repair-a12-models` | fix by hand |
| Hot-deploy a model to a running server | `a12-utilities:deploy-a12-models`, configured in `.claude/a12-deploy-model.json`, written from `.claude/a12-deploy-model.template.json` by `just use`/`just up` for this checkout's stack (deploys the converted models from `build/wcf-output/data/models`, so run `gradle convertModels` first) | restart the server |
| Seed / test data | `a12-test-data:generate-a12-test-data` | write documents by hand under `import/` |
| Coding conventions (frontend, backend, tests, authorization, localization) | `a12-project-setup:coding-practices` | this repo's `CLAUDE.md`, ESLint/Prettier/Checkstyle configs |
| Widget / component docs | A12 docs MCP `search_widget_docs` | — |

After every model-validation run, the `capture-a12-modeling-feedback` skill (if installed) asks the
user to sanity-check the model in the SME/runtime — expect that prompt inside `/spec:apply`; it is
not a failure.

## What a change's `architecture.md` must say about A12

Its `## A12 impact` section lists, per line, what the change touches — `none` where nothing:

- **Models**: each DM/FM/OM/RM/CDM/QM/AM file added or changed, and why that model type.
- **Client**: modules, sagas, middlewares, custom components, localization keys.
- **Server**: listeners, services, JSON-RPC endpoints, migrations.
- **Authorization**: roles (`import/auth/roles.yaml`), ABAC rules (`import/auth/childAuthorizationDefinition.json`).
- **Data**: seed documents, migrations of existing documents.
- **Where it runs**: client vs server for each rule, and why.

## Grill seeds for A12 changes

Questions `/spec:grill` puts on the frontier when a change touches A12 (skip what the artifacts
already settle):

- Model or code? Could a validation / computation rule live in the Document Model instead of a
  listener or saga?
- Which engine renders it — Form, Overview, Relationship, Tree, Content? Why that one?
- Who may see / edit / delete it — which role, which ABAC rule, enforced where?
- Does an existing document change shape? What happens to stored documents (migration)?
- Is a relationship needed, and in which direction (RM + Query Model, or CDM)?
- What does the user see on failure (validation message, localization)?
- Is it covered by a server test, a client test, an e2e test — or only by eye?
