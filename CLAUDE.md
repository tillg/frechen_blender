# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A 3D model of the house "Frechenlehen" (three.js viewer, plan sheets; a dormant Blender 5.2 backend), generated entirely by Python scripts in `code/` from the architect's plans (`input/*.pdf`, rendered to `input/grundriss_eg/og.png`) and detail photos in `input/` (file name = component, e.g. `entrance_door_from_outside.png`). The README (German) is the user-facing doc; keep its component list and script table in sync when adding user-visible features.

The house is described once, in `code/house_core.py` plus `code/ofen.py` (the stoves) `code/desk.py` (the Büro desk) `code/bad.py` (the Bad Großeltern), `code/kueche.py` (the Küche), `code/gaeste_wc.py` (the Gäste-WC), `code/regal.py` (the Büro bookcase), `code/schrankbett.py` (the Yoga room's wall bed) `code/gaestebad.py` (the OG Gästebad), `code/elternbad.py` (the OG Bad Nadine & Till) and `code/waschkueche.py` (basin and shower of the OG Waschküche, house only; all pure Python, no `bpy`/`mathutils`). `house_core.build()` returns a **Blueprint** (`geo`, `parts`, `smooth`, `pivot`, `mat_def`, `paint`, `room_lights`, `garden`, `furniture`, `dims`, `doors`, `plan_rooms`, …); `house_core.build_ofen()` / `build_desk()` / `build_bad()` / `build_kueche()` / `build_gaeste_wc()` / `build_regal()` / `build_schrankbett()` / `build_gaestebad()` / `build_elternbad()` return the Ofen / desk / Bad / Küche / Gäste-WC / Regal / Schrankbett / Gästebad / Elternbad sub-model alone (no house, `garden=None`, dimension lines in `dims`) for `web/ofen.html` / `web/desk.html` / `web/bad.html` / `web/kueche.html` / `web/gaeste_wc.html` / `web/regal.html` / `web/schrankbett.html` / `web/gaestebad.html` / `web/elternbad.html` (all drawn by `web/src/submodel.js`). Three backends turn it into output: `build_house.py` (Blender scene; dormant, see Running), `export_gltf.py` (`.glb` for the three.js viewer in `web/`) and `export_plans.py` (the architect's plan sheets in `plans/`). Make every model change in the core; neither backend nor the viewer repeats its facts (ADR-001-XEWL).

## Running

The live outputs are the three.js viewer (`cd web && npm run dev`, the `.glb` is regenerated from the core) and the plan sheets. After any core change, re-run `python3 code/export_plans.py plans/`: the plan sheets are committed and `tests/test_plans.py` (slow) fails when they are out of date.

### Blender backend (dormant, issue #35)

The Blender output is no longer maintained, for faster dev cycles: no rebuild, no save, no Blender stills, no parity test in the workflow. The scripts (`build_house`, `fire`, `paint`, `windrose`, `garden`, `film`) stay in `code/`; `tests/test_blender_scripts.py` only checks that they compile. `frechenlehen.blend` is frozen at `7805879` (last full check with the parity test green) and not rebuilt since: every later core change is missing from it. To re-enable Blender:

1. Rebuild inside Blender, normally via the Blender MCP server (`mcp__blender__execute_blender_code`), always in this order (`fire`, `paint`, `garden` and `film` depend on objects or materials that `build_house` recreates), then save:

   ```python
   for s in ("build_house", "fire", "paint", "windrose", "garden", "film"):
       exec(open(f"/Users/tgartner/git/frechen_blender/code/{s}.py").read())
   bpy.ops.wm.save_mainfile()
   ```

   Every script is idempotent (re-running replaces its own collection/objects). No hand edits live in the `.blend`; the scripts are the source of truth. Every Blender script imports the core with `sys.path` (`code/` next to the open `.blend`, so each clone builds its own core; no `.blend` open: the caller's `PROJECT`) + `importlib.reload(house_core)`; without the reload a long-running Blender session would silently keep the old core. Without the MCP, the same rebuild runs headless: `Blender -b frechenlehen.blend --python <script that execs the six and saves>`.
2. Restore the parity test from `7805879` (`git checkout 7805879 -- tests/test_blender_parity.py tests/blender/snapshot.py tests/golden/blender_snapshot.json`, plus the `slow` marker text in `pytest.ini`), regenerate the golden (`UPDATE_GOLDEN=1 .venv/bin/python -m pytest -q tests/test_blender_parity.py`), diff it, check with a still (render from a temporary camera to `tmp/details/`, look at it, remove the camera, restore `scene.camera`), and put the rebuild/save/still steps back into this file and `.claude/skills/spec/reference/project.md` (the #35 commit took them out: `git log --grep '#35'`).

Tests:

## Architecture of `house_core.py` (and the Blender backend)

- **Geometry accumulator.** Nothing is created with `bpy.ops`. Builders call `add()` / `box()` / `lbox()` / `sweep()` / `column()` / `prism()` / `boards()`, which append vertices/faces to `GEO[(collection, object)]`; each `add()` call is one **Part** (a closed solid, recorded in `PARTS`). In Blender, `flush_geometry(bp)` turns each entry into one mesh object inside collection `FL_<collection>` under root collection `Haus` and recalculates normals, so face winding does not matter; the glTF backend does the same with `mesh_ops` (ear clipping, per-Part orientation).
- **Local wall frames.** `frame(ax)` returns `P(u, t, z)`: `u` runs along a wall, `t` across it. Wall/door/cladding code is written once in `u/t` and works for both wall orientations.
- **`wall()`** builds an axis-aligned wall with openings `(a, b, sill, head, kind[, shutters])`. The kinds are `W` window, `FD` french door, `GD` glazed larch door (also the big west windows), `D` solid door, and `I` bare opening, filled afterwards by a dedicated builder (`entrance_door`, `back_door`, `stube_niche`, `panel_door`). Exterior openings are recorded in `OPENINGS` (and gable windows in `GABLE_WIN`) so `build_cladding()` can cut the west larch cladding around them. Call cladding after all walls.
- **Interior doors.** Door entries in `interior()` are `(a, b)` for an open passage, or `(a, b, swing, hinge[, flat, style])`. Leaves are opened flat against the room wall by default, 7.5 cm off it so the levers clear it (so the film camera passes freely); every hinged leaf gets black levers on both faces (`door_levers`), sliding leaves flush pulls (`sliding_pulls`), exterior window sashes and FD/GD leaves a room-side handle on the stile towards the middle (`wall()`'s `H`: doors `balkon_klinke()`, windows `fenster_griff()`, after `input/2026-11-16 input/klinke-balkontüre.webp` / `klinke-fenster.webp`); use `flat=False` (90°) where a room corner is too close. `hinge="ab"` makes a double door and `style="glazed"` the Windfang door. Every leaf is recorded in `LEAVES` for clash checks against the walls.
- **Materials.** `MAT_DEF` defines `FL_*` materials: `rgba` for plain colours, `wood` / `speck` for procedural textures in object space, `bump` for plaster. `PAINT` (in the core) overrides the base colour of plain materials only: `FL_Putz`, `FL_Rahmen` (white shutter cross boards), `FL_Laden` (RAL 5014), `FL_Front` (kitchen and Speis cabinets, RAL 5014, fronts from `mallnitz_front()`); `paint.py` applies it in Blender, the viewer reads it from the material extras. Textured materials ignore it. The shutter cross boards are built in the core (`build_cross_boards()`, per storey).
- **`rnd` face attribute.** Each `add()` call gets a random value that the shaders use for per-board/per-slab variation. Parts that overlap in the same plane (frame corners, rails vs. stiles) must share one `rnd` value, otherwise they visibly z-fight. `wall()` and the cladding trims already do this.
- **Stoves in `ofen.py`.** The Ofen sub-model (`OFEN_*`, `ofen_neu()`: stove, benches, bed with mattress and checked blanket), its placement `ofen_im_haus()` and `werkstattofen()` live in `code/ofen.py`, so the stove can be worked on apart from the house. `house_core` imports it and calls those functions; `ofen.py` reaches the primitives and `GEO`/`PARTS` as `hc.*` (`import house_core as hc`; the modules import each other, so no `from house_core import …`). Materials stay in `MAT_DEF`. Blender scripts that build (`build_house.py`, `garden.py`) `reload(ofen)`, `reload(desk)`, `reload(bad)`, `reload(kueche)`, `reload(gaeste_wc)`, `reload(regal)`, `reload(schrankbett)`, `reload(gaestebad)`, `reload(elternbad)` and `reload(waschkueche)` before `reload(house_core)`.

## Other scripts

- `garden.py` (collection `Garten`): the meadow is a Geometry Nodes scatter of grass-clump instances on an emitter grid, with 10 % density in the viewport. Where grass grows, the clump shape and the shrub placements come from the **garden layout** in the core (`garden_layout()`: `NO_GRASS` bounding boxes computed from `GEO`, the windrose area from `WINDROSE_CENTER`/`WINDROSE_R`, density, clump, shrubs). It plants the leafy shrubs into the `Beet_*` beds.
- `export_plans.py`: the third backend (standard library only): Blueprint → six plan sheets for the architect in `plans/` (`eg`, `og`, `nord`, `ost`, `sued`, `west`.svg; A3 at 1:100, mm `viewBox`). Grundriss = section of the closed Parts at `CUT` (which objects are walls, frames, floors, ground or extras: the core's `PLAN`; walls hatched inside their union outline), projection below it without `FURNITURE`, the stair as the architect's symbol from `STAIRS` (outline, risers, walking line with circle at the bottom and arrow up, in its bottom storey `15 STG 18.0/25.5`; `PLAN` `stair_objects` are neither cut nor projected), door swings from `DOORS` (the conventional 90° symbol; the leaf as built, `DOORS` `leaf`, is left out), rooms from `PLAN_ROOMS` (area = region of a section at `ROOM_CUT`), dimension chains scanned from the section; Ansicht = painter's hidden-line projection with level marks. Deterministic (model-state hash, no date); `plans/` is committed.
- `export_gltf.py`: Blueprint → `.glb` (standard library only). One node per GEO object (`extras.collection`, `extras.smooth`, `extras.furniture` for the objects of the last viewer stage "Eingerichtet"), one primitive per material with `POSITION`/`NORMAL`/`_RND`, `MAT_DEF` + paint in material extras, room lights and the garden layout in `scene.extras`, positions as `(x, z, -y)`. `web/public/frechenlehen.glb` is generated (`npm run blueprint`, run before `dev`/`build`/`test`) and git-ignored.
- `web/` (Vite, three.js `WebGPURenderer` + TSL, ADR-003-SKGB): `blueprint.js` (load), `stages.js` (timeline weights), `materials.js` (TSL from the extras), `ink.js` (Skizze lines), `lighting.js` (day/dusk, room lights), `garden.js`, `ui.js`, `tour.js` (Rundgang), `markers.js` (Vorlagen links), `vorlagen.js` + `vorlagen-data.js` (photo pages), `main.js`. A dev-only test hook is `window.__fl`. GitHub Pages deploys `web/dist` from `main` (`.github/workflows/pages.yml`).
- `tour.py` (pure Python, own file so the route can be edited apart from house and film): `ROUTE` is a list of `orbit` / `path` / `turn` / `stair` / `hold` segments (`turn` turns on the spot at `TURN` °/s, left `L` or right `R`; `peek()` = look along a room's left wall, then swing right; the pauses are `PAUSE` s; a `path` first turns at `TURN` to face its way); `build_tour()` bakes it to smoothed per-frame camera keys `(x, y, z, yaw, pitch, lens)`. `film.py` keys `FL_Kamera_Rundgang` with them (plus fill lights in collection `Innenlicht`); `export_gltf.py` writes them to `scene.extras.tour`, which the viewer's "Rundgang" (`web/src/tour.js`) plays. `tests/golden/tour.json` pins the keys; after a deliberate route change: `UPDATE_TOUR_GOLDEN=1 python3 -m pytest -q tests/test_tour.py`. The route is closed (it ends at its start pose), so `build_tour()` smooths cyclically and the viewer can loop it. After changing the route or furniture, the pure-Python route tests in `tests/test_tour.py` check clearance of the Wandlampen and the Speis/Essen built-ins; the full check against all geometry (sample every frame, BVH `find_nearest` ≥ 0.25 m plus a `ray_cast` between consecutive frames) needs Blender and is dormant with it.
- `vorlagen.py` (pure Python, issue #31): `BEREICHE` sorts every raster image of `input/` into one Bereich (key, title, PLAN_ROOMS room, marker anchor or `None`, pictures with copy name and caption); `tests/test_vorlagen.py` fails when a new picture is not assigned and copied. `--copy` (macOS `sips`) writes the committed copies `web/public/vorlagen/<key>/*.jpg` (≤ 1600 px); `vorlagen.py <out.json>` writes `web/public/vorlagen.json` (`npm run blueprint`, git-ignored) for `web/vorlagen.html` (index; `?b=<key>` one Bereich). `export_gltf.py` writes the anchors to `scene.extras.vorlagen` and the wall objects to `vorlagen_walls`; `web/src/markers.js` puts a link per anchor over the house viewer (hidden behind walls, in routes, `?hires=on` and on plan sheets).
- `fire.py` (collection `Feuer`): the flickering-fire component. `tongues(w, h)` (pure, also used by `export_gltf.py` → `scene.extras.fires` → `web/src/fire.js`) lays out flame tongues on each bed in `house_core.FIRES` (recorded by the stoves); in Blender each tongue flickers via F-curve noise, plus a flickering light per fire.
- `windrose.py`: its own collection, independent of the rebuild.

## Pitfalls seen in this project

- **Coplanar faces with the same normal z-fight.** Offset new parts by millimetres (e.g. the stairwell edge boards stand 6 mm proud of the slab edge) rather than aligning them with existing faces.
- **Reading the plans.**
  - Pink-hatched wall in `grundriss_eg.png` is wall, not an opening. The original vector extraction only read gray wall fills. The pink coloring is only for the Behörde: It shows what are new constructual elemenst.
  - A wall segment with lighter hatching is a closed-up door. Two parallel lines without hatching between hatched wall stubs are an opening (e.g. the Großeltern Bad opens to the bedroom).
  - Stair: 15 risers at 18.0/25.5 need 3.57 m of run, more than the plan draws ("Treppe wird verschoben"). The OG stairwell opening confirms the full length.
  - To map world coordinates to plan pixels, use the page transform in `build_references()` (1:100, 28.3465 pt/m).
- **Render look.** EEVEE with the AgX view transform washes out strong emission and bright saturated colours. Keep emission strengths low (the stove fire uses 1.2).
- **Waiting for a background check.** `until ! pgrep -f "check.sh full"; do sleep 5; done` matches its own shell and never ends: wait on the PID, or write `pgrep -f "[c]heck.sh full"`.

## Working rules

- **Subagents first** for search-heavy, parallelizable or multi-file work. Use `explorer` / `researcher` / `worker` (cheaper models), not `general-purpose` (runs on Opus).
- **Never mock** anything without explicit permission. **Never make tests pass by changing/removing them** without explicit permission.
- **Branches:** one per issue (`issue/<n>-<slug>`, created at `[wip]`, deleted after its merge; see Spec-driven workflow › GitHub issues). Any other branch, or switching branches outside that flow, only with explicit permission. Git worktrees go in `.worktrees/`.
- **Verify before claiming done**: after each change the quick check (`check.sh quick` + the change's own test) and a Show; the full check (`check.sh full`) at the end of `/spec:apply` and at `/spec:archive`. "Looks right" is not done.
- **Be extremely concise when reporting.** Sacrifice grammar for concision.
- **Consult the advisor** before a large plan, when an error repeats, and before calling a long task done.
- **Web apps (three.js viewer):** before calling it done, look at it on the dev server: a `web/shot.js` screenshot of the Show URL (works when the Playwright MCP is down), or the Playwright MCP. Never report a visual change as working without having seen it in a screenshot: zoom on the changed spot, check edges/last row/outer column too, use `scale:"css"` (1×) for fine lines, and say what exactly was checked. Reproduce a user-reported glitch before fixing it. Give the user an `http://localhost` URL (fresh query, never a fresh port) to reload, not `file://`. Artifacts go to `tmp/`.
- **Exactly one dev server, never more.** It runs on port 5377 (`cd web && npm run dev`, pinned with `--strictPort`) and serves both pages: Haus `http://localhost:5377/`, Ofen `http://localhost:5377/ofen.html`; under `http://localhost:5377/frechen_blender/` it also serves the production build `web/dist/` as GitHub Pages does (`web/serve-build.js`; `npm run build` refreshes it). If something already listens on 5377 (`lsof -iTCP:5377 -sTCP:LISTEN`), reuse it, also when another session started it; start it only if the port is free, and never on another port. A saved `code/*.py` makes the server re-run `npm run blueprint` and reload open pages (`web/blueprint-watch.js`); the view survives the reload because it lives in the URL (`?cam=&at=&p=&cut=`, Ofen `?cam=&at=&look=`). The tests use this server too; no exception, not even for a test run.
- **Long-running processes (>~30 s, e.g. the film render):** tee to `tmp/<name>-$(date +%Y%m%d-%H%M%S).log`, `open` the log, run in the background, check at least every 10 min; no progress for ~10 min → treat as stuck.
- **ETAs** are absolute, Europe/Berlin, `YYYY-MM-DD HH:MM`.
- **Diagrams:** compact ASCII in chat; important ones as Mermaid in `docs/diagrams/<name>.mmd` (plus `.svg` when a visual diagram is asked for).

## Spec-driven workflow

Every non-trivial change goes through the `spec` plugin (`.claude/skills/spec/`):

```
propose → [grill | iterate] → apply → adversarial-code-review → archive
small change:  tweak
```

- Start reading at `specs/README.md`; `specs/system/` is the truth about the model today,
  `specs/architecture/index.md` lists the binding ADRs (cite them by full `ADR-NNN-HHHH` id).
- `/spec:overview` shows where every open change stands; the `/spec-status` pane shows it live.
- Project commands and step kinds (`[python]`, `[web]`; `[blender]` dormant):
  `.claude/skills/spec/reference/project.md`.
- Choices made while nobody was there to ask go into `DECISIONS.md`
  (`.claude/skills/spec/reference/decisions.md`).

### GitHub issues

Work is tracked as issues in `tillg/frechen_blender`. Each issue carries exactly **one** state label (in brackets, to tell them from topic labels like `plan`, `system`);
a transition swaps it: `gh issue edit <n> --remove-label <old> --add-label <new>`.

```
[new] → [wip] → [testing] → [under review] → [done]    (red check or review findings → back to [wip])
```

Work on an issue always starts with its branch, before any other step: `git switch main && git pull
&& git switch -c issue/<n>-<slug>`, then label `[wip]`.

| Label | Set when | Step |
|---|---|---|
| `[new]` | the issue is filed | — |
| `[wip]` | work starts: branch `issue/<n>-<slug>` from current `main`, change dir `specs/changes/<n>-<slug>/` (the pane matches branch and change by the last path segment) | `/spec:propose` or `/spec:tweak` |
| `[testing]` | the final check starts (`check.sh full`); not for the per-step quick check. Red → back to `[wip]` | end of `/spec:apply` |
| `[under review]` | final check green, `/spec:adversarial-code-review` done; work committed on the branch (with approval), pushed, PR opened with `Closes #<n>`. Waits for a human; requested changes → back to `[wip]` | — |
| `[done]` | after the human's approval: `/spec:archive` on the branch (digest the change into `specs/system/` and ADRs, delete the change dir), push, `gh pr merge <pr> --merge --delete-branch` (closes the issue, deletes the branch), `git switch main && git pull` | `/spec:archive` + merge |

A tweak without an issue stays as before: one commit on `main`, no labels.
