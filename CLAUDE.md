# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Blender 5.2 model of the house "Frechenlehen", generated entirely by Python scripts in `code/` from the architect's plans (`input/*.pdf`, rendered to `input/grundriss_eg/og.png`) and detail photos in `input/` (file name = component, e.g. `entrance_door_from_outside.png`). The README (German) is the user-facing doc; keep its component list and script table in sync when adding user-visible features.

The house is described once, in `code/house_core.py` plus `code/ofen.py` (the stoves) `code/desk.py` (the Büro desk) `code/bad.py` (the Bad Großeltern), `code/kueche.py` (the Küche), `code/gaeste_wc.py` (the Gäste-WC) and `code/regal.py` (the Büro bookcase; all pure Python, no `bpy`/`mathutils`). `house_core.build()` returns a **Blueprint** (`geo`, `parts`, `smooth`, `pivot`, `mat_def`, `paint`, `room_lights`, `garden`, `furniture`, `dims`, `doors`, `plan_rooms`, …); `house_core.build_ofen()` / `build_desk()` / `build_bad()` / `build_kueche()` / `build_gaeste_wc()` / `build_regal()` return the Ofen / desk / Bad / Küche / Gäste-WC / Regal sub-model alone (no house, `garden=None`, dimension lines in `dims`) for `web/ofen.html` / `web/desk.html` / `web/bad.html` / `web/kueche.html` / `web/gaeste_wc.html` / `web/regal.html` (all drawn by `web/src/submodel.js`). Three backends turn it into output: `build_house.py` (Blender scene), `export_gltf.py` (`.glb` for the three.js viewer in `web/`) and `export_plans.py` (the architect's plan sheets in `plans/`). Make every model change in the core; neither backend nor the viewer repeats its facts (ADR-001-XEWL).

## Running

The scripts run *inside* Blender, normally via the Blender MCP server (`mcp__blender__execute_blender_code`):

```python
for s in ("build_house", "fire", "paint", "windrose", "garden", "film"):
    exec(open(f"/Users/tgartner/git/frechen_blender/code/{s}.py").read())
bpy.ops.wm.save_mainfile()
```

Always rebuild in this order: `fire`, `paint`, `garden` and `film` all depend on objects (or materials) that `build_house` recreates. Every script is idempotent (re-running replaces its own collection/objects). No hand edits live in the `.blend`; the scripts are the source of truth. Every Blender script imports the core with `sys.path` (`code/` next to the open `.blend`, so each clone builds its own core; no `.blend` open: the caller's `PROJECT`) + `importlib.reload(house_core)`; without the reload a long-running Blender session would silently keep the old core. Without the MCP, the same rebuild runs headless: `Blender -b frechenlehen.blend --python <script that execs the six and saves>`. After any core change, also re-run `python3 code/export_plans.py plans/`: the plan sheets are committed and `tests/test_plans.py` (slow) fails when they are out of date.

Tests:

- Environment: a repo-local `.venv` (`python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt`, git-ignored); tests run with `.venv/bin/python` (`npm run blueprint` keeps the stdlib `python3`). `cd web && npm install`.
- Two tiers, `scripts/check.sh` runs and times them (log in `tmp/check-<ts>.log`): `bash scripts/check.sh quick` (`pytest -m "not slow"` + Vitest, ≤ 60 s) after every change, together with the change's own new test run alone; `bash scripts/check.sh full` (all pytest incl. `slow` = Blender parity, `npm test`, all Playwright) once at the end of a change, at archive and on request. Playwright's `@eye` test (stills along the Rundgang) is not in the default run: `npx playwright test --grep @eye`.
- `.venv/bin/python -m pytest -q` (repo root): core, `mesh_ops`, glTF export, and the **parity test**, which builds headless in Blender and compares a per-object fingerprint with `tests/golden/blender_snapshot.json`; it also checks that the saved `frechenlehen.blend` is the current build. A deliberate change to the Blender output: regenerate with `UPDATE_GOLDEN=1 python3 -m pytest -q tests/test_blender_parity.py`, diff the golden, then rebuild and save the `.blend`.
- `cd web && npm test && npx playwright test`: Vitest units and Playwright e2e (projects `dev` and `preview`, the latter on the production build under `/frechen_blender/`, built first by the setup project `build`). Both run against the one dev server on 5377; Playwright starts no server of its own (only `npm run dev` on 5377 if nothing runs there). Headless Chromium runs on the real GPU (`--use-angle=metal`); WebGPU is off there, so the viewer runs on its WebGL2 fallback. Screenshots go to `tmp/web/`.
- **Show** (the visual check of a core or viewer change): `.venv/bin/python code/show.py <object…> --print` computes a view URL from the Blueprint that frames the objects (outside: nearest facade; inside: from above, storeys above cut away; `--from n|e|s|w|top`, `--page ofen|desk|bad|kueche|gaeste_wc|regal`, `--at x,y,z`). Look at it first: `cd web && node shot.js '<url>' ../tmp/web/<name>.png`, read it at 1× (hidden → retry with `--from`); then `.venv/bin/python code/show.py <object…>` opens it in the user's browser. `show.py` refuses (exit 2) when the server on 5377 runs from another clone.
- Blender stills are still needed for Blender-only changes (per step) and once at the end of a change that touched the Blender output: render from a temporary camera to `tmp/details/` and look at them (then remove the temp camera and restore `scene.camera`).

## Architecture of `house_core.py` (and the Blender backend)

- **Geometry accumulator.** Nothing is created with `bpy.ops`. Builders call `add()` / `box()` / `lbox()` / `sweep()` / `column()` / `prism()` / `boards()`, which append vertices/faces to `GEO[(collection, object)]`; each `add()` call is one **Part** (a closed solid, recorded in `PARTS`). In Blender, `flush_geometry(bp)` turns each entry into one mesh object inside collection `FL_<collection>` under root collection `Haus` and recalculates normals, so face winding does not matter; the glTF backend does the same with `mesh_ops` (ear clipping, per-Part orientation).
- **Local wall frames.** `frame(ax)` returns `P(u, t, z)`: `u` runs along a wall, `t` across it. Wall/door/cladding code is written once in `u/t` and works for both wall orientations.
- **`wall()`** builds an axis-aligned wall with openings `(a, b, sill, head, kind[, shutters])`. The kinds are `W` window, `FD` french door, `GD` glazed larch door (also the big west windows), `D` solid door, and `I` bare opening, filled afterwards by a dedicated builder (`entrance_door`, `back_door`, `stube_niche`, `panel_door`). Exterior openings are recorded in `OPENINGS` (and gable windows in `GABLE_WIN`) so `build_cladding()` can cut the west larch cladding around them. Call cladding after all walls.
- **Interior doors.** Door entries in `interior()` are `(a, b)` for an open passage, or `(a, b, swing, hinge[, flat, style])`. Leaves are opened flat against the room wall by default, 7.5 cm off it so the levers clear it (so the film camera passes freely); every hinged leaf gets black levers on both faces (`door_levers`), sliding leaves flush pulls (`sliding_pulls`), FD/GD leaves a room-side handle (`olive`); use `flat=False` (90°) where a room corner is too close. `hinge="ab"` makes a double door and `style="glazed"` the Windfang door. Every leaf is recorded in `LEAVES` for clash checks against the walls.
- **Materials.** `MAT_DEF` defines `FL_*` materials: `rgba` for plain colours, `wood` / `speck` for procedural textures in object space, `bump` for plaster. `PAINT` (in the core) overrides the base colour of plain materials only: `FL_Putz`, `FL_Rahmen` (white shutter cross boards), `FL_Laden` (RAL 5014), `FL_Front` (kitchen and Speis cabinets, RAL 5014, fronts from `mallnitz_front()`); `paint.py` applies it in Blender, the viewer reads it from the material extras. Textured materials ignore it. The shutter cross boards are built in the core (`build_cross_boards()`, per storey).
- **`rnd` face attribute.** Each `add()` call gets a random value that the shaders use for per-board/per-slab variation. Parts that overlap in the same plane (frame corners, rails vs. stiles) must share one `rnd` value, otherwise they visibly z-fight. `wall()` and the cladding trims already do this.
- **Stoves in `ofen.py`.** The Ofen sub-model (`OFEN_*`, `ofen_neu()`: stove, benches, bed with mattress and checked blanket), its placement `ofen_im_haus()` and `werkstattofen()` live in `code/ofen.py`, so the stove can be worked on apart from the house. `house_core` imports it and calls those functions; `ofen.py` reaches the primitives and `GEO`/`PARTS` as `hc.*` (`import house_core as hc`; the modules import each other, so no `from house_core import …`). Materials stay in `MAT_DEF`. Blender scripts that build (`build_house.py`, `garden.py`) `reload(ofen)`, `reload(desk)`, `reload(bad)`, `reload(kueche)`, `reload(gaeste_wc)` and `reload(regal)` before `reload(house_core)`.
- **Desk in `desk.py`.** `desk_neu(c, x0, y0)` builds table, monitors, MacBook, keyboard and trackpad straight into collection `c` (house: `EG` at `DESK_AT`; sub-model: `Desk` at the origin), `stuhl()` the chair; the devices draw `rnd` from their own `random.Random`, so no later part shifts. The screen panes are objects with a `PIVOT` (lower-left corner) and a `TURN` (yaw); their materials carry `image` (under `web/public/`) and `size`, mapped in object space in both backends (`house_core.local()`). The textures are committed JPEGs, made once with `sips` from `input/2026-11-06 input/`.
- **Bad Großeltern in `bad.py`.** `bad_neu(c, x0, y0)` builds the bathroom straight into collection `c` with the room's inner SW corner at (x0, y0) (house: `EG` at `BAD_AT`; sub-model: `Bad` at the origin): its own walls (12 cm niche wall, lintel, 1 m low wall), glass, walk-in shower with limestone cladding, the Doppelwaschbecken (`hc.waschbecken()`), toilet + WC tiles (`wainscot`), the white cabinets (`_Schrank`) and the two interlocking sliding leaves (WC leaf open, both recorded in `LEAVES`; one object each, `_Schiebetuer_hinten` / `_vorne`, with their travel in `SLIDE` → `Blueprint.slide` → glTF `extras.slide`, which `submodel.js` and `main.js` (stage Eingerichtet, not in the Rundgang) animate via `slides.js`: every 4 s one random leaf rolls to its other end in 2 s). Dimensions follow the agreed drawing `input/2026-11-08 input/grosseltern_v4.svg`. It lays its own floor (`floor()`: limestone strip as wide as the WC along the west wall, oak elsewhere, own `random.Random`); the core leaves the room (`BAD_EG`) out of the EG floor.
- **Küche in `kueche.py`.** `kueche_neu(c, x0, y0)` builds the kitchen straight into collection `c` with the room's inner NW corner (Speis wall × Flur wall) at (x0, y0) (house: `EG` at `KUECHE_AT`; sub-model: `Kueche` at the origin, so it lies at y ≤ 0); positions are written in house coordinates and shifted. Sink run, east run, peninsula, Wamsler (`ofen.wamsler`) and hood, wall cabinets, Besenschrank, flue box (`_Waende`). Layout: the agreed drawing `input/2026-11-09 input/speis_kueche_v6.svg` (generator beside it). The room's walls, the kitchen door and the Speis (`speis()` in the core: shelves, cabinet, sliding leaf) stay in `house_core`.
- **Gäste-WC in `gaeste_wc.py`.** `gaeste_wc_neu(c, x0, y0)` builds WC + Garderobe by the back hall straight into collection `c` with the old WC room's inner SW corner at (x0, y0) (house: `EG` at `WC_AT`; sub-model: `GaesteWC` at the origin); positions are written in house coordinates and shifted, as the hand basin stands outside the room on the Flur east wall. It brings its walls (the new partition and the WC's north wall with the outward WC door and the open Garderobe passage), the toilet and WC tiles (`wainscot`), the basin (`hc.waschbecken()`, einzeln 40 × 28 on its Ständer) with tiles (`wainscot(sides="e")`) and a wood-framed mirror, and the Garderobe (`_Garderobe`: bench, hook board, hooks, hat shelf). It also builds the back hall's other two doors (`back_door(c, dx, dy)` and the glazed Windfang door via `panel_door(..., leaf=)`): the three leaves (`_Hintertuer`, `_WC_Tuer`, `_Windfangtuer`) are objects of their own with a `PIVOT` at the hinge and a `SWING` (degrees to their other state) → `Blueprint.swing` → glTF `extras.swing`, which `submodel.js` and `main.js` (stage Eingerichtet, not in the Rundgang; the film keeps them as built) animate via `slides.js` (every 3 s one random door swings in 3 s). Layout: the agreed drawing `input/2026-11-10 input/gaeste_wc_v3.svg` (generator beside it). The floor stays the core's limestone (`GAESTE_WC_EG`, none under the partition: `TRENNWAND_EG`).
- **Schrank im Büro in `regal.py`.** `regal_neu(c, x0, y0, walls=False)` builds the Tegernsee bookcase around the Bibliothek's east window into collection `c` with the room's inner SE corner (east wall x Flur wall) at (x0, y0) (house: `EG` at `REGAL_AT`, object `EG_Moebel`, i.e. furniture; sub-model: `Regal` at the origin, the room at x < 0, `walls=True` adds the pieces of the east, north and Flur walls via `waende()`). The three openings there are defined once in `regal.py` (`FENSTER`, `BALKONTUER`, `TUER`: the Büro door moved `SHIFT` = 50 cm west so its leaf, open 90°, clears the south column) and `build_eg()` uses them; `tuer(c)` makes the leaf an object of its own (`<c>_Buerotuer`, `PIVOT` + `SWING`), which the viewer swings on its own clock (`slides.js`: 2 s swing, 4 s rest). Own `random.Random(14)`. `vitrine(c)` builds the set's narrow 52 element (glazed vitrine) in the Bibliothek's NW corner behind the piano (`VITRINE_AT`, house only, own `random.Random(15)`). Layout: the agreed drawing `input/2026-11-11 input/buero_regal_v2.svg` (generator beside it).
- **`PIVOT`** puts an object's origin at a hinge (`TURN` adds a yaw about it; both backends store the mesh unturned). Besides the screen panes, the back hall's three doors and the Büro door (`SWING`), only `EG_Haustuer` uses it; `film.py` swings it open by rotating it 90° about z.
- Coordinates are in metres: origin at the outer SW corner, +X east, +Y north. Constants such as `Z_OG`, `STAIR_HOLE`, `FOOT`, `CORRIDOR_EG` and the stair constants `ST_*` are shared between builders.

## Other scripts

- `garden.py` (collection `Garten`): the meadow is a Geometry Nodes scatter of grass-clump instances on an emitter grid, with 10 % density in the viewport. Where grass grows, the clump shape and the shrub placements come from the **garden layout** in the core (`garden_layout()`: `NO_GRASS` bounding boxes computed from `GEO`, the windrose area from `WINDROSE_CENTER`/`WINDROSE_R`, density, clump, shrubs). It plants the leafy shrubs into the `Beet_*` beds.
- `export_plans.py`: the third backend (standard library only): Blueprint → six plan sheets for the architect in `plans/` (`eg`, `og`, `nord`, `ost`, `sued`, `west`.svg; A3 at 1:100, mm `viewBox`). Grundriss = section of the closed Parts at `CUT` (which objects are walls, frames, floors, ground or extras: the core's `PLAN`; walls hatched inside their union outline), projection below it without `FURNITURE`, the stair as the architect's symbol from `STAIRS` (outline, risers, walking line with circle at the bottom and arrow up, in its bottom storey `15 STG 18.0/25.5`; `PLAN` `stair_objects` are neither cut nor projected), door swings from `DOORS` (the conventional 90° symbol; the leaf as built, `DOORS` `leaf`, is left out), rooms from `PLAN_ROOMS` (area = region of a section at `ROOM_CUT`), dimension chains scanned from the section; Ansicht = painter's hidden-line projection with level marks. Deterministic (model-state hash, no date); `plans/` is committed.
- `export_gltf.py`: Blueprint → `.glb` (standard library only). One node per GEO object (`extras.collection`, `extras.smooth`, `extras.furniture` for the objects of the last viewer stage "Eingerichtet"), one primitive per material with `POSITION`/`NORMAL`/`_RND`, `MAT_DEF` + paint in material extras, room lights and the garden layout in `scene.extras`, positions as `(x, z, -y)`. `web/public/frechenlehen.glb` is generated (`npm run blueprint`, run before `dev`/`build`/`test`) and git-ignored.
- `web/` (Vite, three.js `WebGPURenderer` + TSL, ADR-003-SKGB): `blueprint.js` (load), `stages.js` (timeline weights), `materials.js` (TSL from the extras), `ink.js` (Skizze lines), `lighting.js` (day/dusk, room lights), `garden.js`, `ui.js`, `tour.js` (Rundgang), `main.js`. A dev-only test hook is `window.__fl`. GitHub Pages deploys `web/dist` from `main` (`.github/workflows/pages.yml`).
- `tour.py` (pure Python, own file so the route can be edited apart from house and film): `ROUTE` is a list of `orbit` / `path` / `turn` / `stair` / `hold` segments (`turn` turns on the spot at `TURN` °/s, left `L` or right `R`; `peek()` = look along a room's left wall, then swing right; the pauses are `PAUSE` s; a `path` first turns at `TURN` to face its way); `build_tour()` bakes it to smoothed per-frame camera keys `(x, y, z, yaw, pitch, lens)`. `film.py` keys `FL_Kamera_Rundgang` with them (plus fill lights in collection `Innenlicht`); `export_gltf.py` writes them to `scene.extras.tour`, which the viewer's "Rundgang" (`web/src/tour.js`) plays. `tests/golden/tour.json` pins the keys; after a deliberate route change: `UPDATE_TOUR_GOLDEN=1 python3 -m pytest -q tests/test_tour.py`. The route is closed (it ends at its start pose), so `build_tour()` smooths cyclically and the viewer can loop it. After changing the route or furniture, check that the camera clears all geometry: sample every frame and use a BVH `find_nearest` distance (≥ 0.25 m) plus a `ray_cast` between consecutive frames.
- `fire.py` (collection `Feuer`): the flickering-fire component. `tongues(w, h)` (pure, also used by `export_gltf.py` → `scene.extras.fires` → `web/src/fire.js`) lays out flame tongues on each bed in `house_core.FIRES` (recorded by the stoves); in Blender each tongue flickers via F-curve noise, plus a flickering light per fire.
- `windrose.py`: its own collection, independent of the rebuild.

## Pitfalls seen in this project

- **Coplanar faces with the same normal z-fight.** Offset new parts by millimetres (e.g. the stairwell edge boards stand 6 mm proud of the slab edge) rather than aligning them with existing faces.
- **Reading the plans.**
  - Pink-hatched wall in `grundriss_eg.png` is wall, not an opening. The original vector extraction only read gray wall fills. The pink coloring is only for the Behörde: It shows what are new constructual elemenst.
  - A wall segment with lighter hatching is a closed-up door. Two parallel lines without hatching between hatched wall stubs are an opening (e.g. the Großeltern Bad opens to the bedroom).
  - Stair: 15 risers at 18.0/25.5 need 3.57 m of run, more than the plan draws ("Treppe wird verschoben"). The OG stairwell opening confirms the full length.
  - To map world coordinates to plan pixels, use the page transform in `build_references()` (1:100, 28.3465 pt/m).
- **Render look.** EEVEE with the AgX view transform washes out strong emission and bright saturated colours. Keep emission strengths low (the stove fire uses 1.2).

## Claude config: everything comes from this repo

User-wide Claude config (`~/.claude/…`) is switched off for this project (`.claude/settings.json`, `.claude/settings.local.json`), so all instructions, agents, MCP servers and settings live in the repo. The `spec` plugin in `.claude/skills/spec/` is copied from agents1.

A project file cannot remove user-scope hooks and status line (`disableAllHooks` would also disable the spec pane), permission allow-lists, `autoMode`, or UI settings. For a fully clean session, start with `claude --setting-sources project,local`.

## Working rules

- **Subagents first** for search-heavy, parallelizable or multi-file work. Use `explorer` / `researcher` / `worker` (cheaper models), not `general-purpose` (runs on Opus).
- **Never mock** anything without explicit permission. **Never make tests pass by changing/removing them** without explicit permission.
- **Never create or switch branches** without explicit permission. Git worktrees go in `.worktrees/`.
- **Verify before claiming done**: after each change the quick check (`check.sh quick` + the change's own test) and a Show; the full check (`check.sh full`, after a Blender rebuild/save/still if the Blender output changed) at the end of `/spec:apply` and at `/spec:archive`. "Looks right" is not done.
- **Be extremely concise when reporting.** Sacrifice grammar for concision.
- **Consult the advisor** before a large plan, when an error repeats, and before calling a long task done.
- **Web apps (three.js viewer):** before calling it done, look at it on the dev server: a `web/shot.js` screenshot of the Show URL (works when the Playwright MCP is down), or the Playwright MCP. Never report a visual change as working without having seen it in a screenshot: zoom on the changed spot, check edges/last row/outer column too, use `scale:"css"` (1×) for fine lines, and say what exactly was checked. Reproduce a user-reported glitch before fixing it. Give the user an `http://localhost` URL (fresh query, never a fresh port) to reload, not `file://`. Artifacts go to `tmp/`.
- **Exactly one dev server, never more.** It runs on port 5377 (`cd web && npm run dev`, pinned with `--strictPort`) and serves both pages: Haus `http://localhost:5377/`, Ofen `http://localhost:5377/ofen.html`; under `http://localhost:5377/frechen_blender/` it also serves the production build `web/dist/` as GitHub Pages does (`web/serve-build.js`; `npm run build` refreshes it). If something already listens on 5377 (`lsof -iTCP:5377 -sTCP:LISTEN`), reuse it, also when another session started it; start it only if the port is free, and never on another port. A saved `code/*.py` makes the server re-run `npm run blueprint` and reload open pages (`web/blueprint-watch.js`); the view survives the reload because it lives in the URL (`?cam=&at=&p=&cut=`, Ofen `?cam=&at=&look=`). The tests use this server too; no exception, not even for a test run.
- **Long-running processes (>~30 s, e.g. the film render):** tee to `tmp/<name>-$(date +%Y%m%d-%H%M%S).log`, `open` the log, run in the background, check at least every 10 min; no progress for ~10 min → treat as stuck.
- **ETAs** are absolute, Europe/Berlin, `YYYY-MM-DD HH:MM`.
- **Diagrams:** compact ASCII in chat; important ones as Mermaid in `docs/diagrams/<name>.mmd` (plus `.svg` when a visual diagram is asked for).
